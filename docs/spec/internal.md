# 情報の流れとモジュール構成

更新日：2026-10-18。構造は[全体クラス図](../../architecture.md)、関数とデータは[入出力契約](contracts.md)を正本とする。

## 1 共通設計

計算は純関数で、DB・API・時計を知らない。外部接続、日時変換、時間帯調整の仮ルールを交換可能にする。本人用の最新完成版と共有用固定版を分ける。UIのみの機能は受付に進ませない。

## 2 受付と実行

~~~mermaid
flowchart TD
    UI[Web依頼] --> MODE{実行モード}
    MODE -->|UIのみ| PREVIEW[準備中または表示デモ]
    MODE -->|モックまたは実接続| RECEIVE[依頼と本人と入力を検証]
    LINE[LINE Webhook] --> SIGN[生本文の署名と依頼を検証]
    SIGN --> RECEIVE
    RECEIVE --> ACCEPT[耐久受付とrun_id発行]
    ACCEPT --> QUEUE[queued: 待ち行列]
    ACCEPT --> ACK[受付済みを応答]
    QUEUE --> CLAIM[内部の実行担当が実行権を取得]
    CLAIM --> RUN[running: 権限と版を再確認]
    RUN --> KIND{依頼の種類}
    KIND -->|カレンダー更新| PROCESS[必要な取得または保存済み入力から計算]
    KIND -->|LINE依頼| SAVED[保存済み完成版と画像を固定し検証]
    PROCESS --> SAVE[同じ入力版の完成結果を検証し保存]
    SAVE --> PUB[所有者と版を確認して最新参照を切替]
    PUB --> VIEW[本人表示用データ]
    PUB --> IMAGE[WebUI共有部分の画像化と保存]
    IMAGE --> READY[画像準備結果を記録]
    SAVED --> SHARE[同一版の候補カードともっと見るまたは正常0件案内]
    SHARE --> SEND[現在の許可を再確認して送信]
    SEND --> END[受理または拒否または結果不明を記録]
~~~

受付と実行の具体基盤はP05。永続キューの有無・起動通知・claim・停止検出・再試行・同一利用者の順序制御を検証する。単なるOperationRunのqueued保存やメモリロックで耐久実行を保証しない。秘密を必要とする非同期送信用情報の安全な引渡し・保持はP05/P07で決め、通常ログへ書かない。

モックの通し検証はfixture_check。実Google／実LINEへ暗黙に接続しない。受付には永続的な処理入力が必要で、コードの関数参照だけをブラウザから渡さない。

## 3 モジュール責務

| ID | モジュール | 責務 |
| --- | --- | --- |
| M01 | 設定・ユーザー識別 | 本人、設定、版、LINE対応。自己申告IDを本人連携として採用しない |
| M02 | 受付・更新制御 | 受付と実行の境界、必要な再処理、実行状態、古い結果の排除 |
| M03 | カレンダー取得 | モック／Google、全ページ・繰返し・対象範囲の取得 |
| M04 | 予定正規化 | 入力を計算用共通形式へ変換・検証。日跨ぎ分割は担当しない |
| M05 | 計算区間生成・調整・集計 | 日跨ぎ切出し・時間重複統合、仮調整ルール、日別／時間別計算 |
| M06 | 候補選出 | 対象日・除外・上限・順位・最終出力の検証 |
| M08 | 表示・画像・カード組立 | 更新時は完成版のWebUI共有部分を画像化。LINE時は保存済み画像と候補から説明付きカードともっと見るを作る |
| M09 | 保存 | 形式変換・所有者／参照／版検証・保存・最新完成版の切替 |
| M11 | LINE受付・送信 | 署名・依頼判定、本人とグループ許可、固定版返信、再送の照合 |
| 共通 | 日時・時計アダプター | 呼出側でtoday・対象日・オフセット等を決め、計算へ明示する |

M07（AI）・M10（詳細開発者画面）は将来。別サーバー化を必須とせず、同一アプリでも責務を分ける。JobQueue／Workerは論理的な役割で、採用サービスは未決。

## 4 更新の種類

| 契機 | 読込・保存・再処理 |
| --- | --- |
| Web起動・手動更新 | 全取得→正規化→調整→計算→候補→完成版保存・公開→共有用画像保存 |
| 許可済み＠リスケ | 保存済み完成版と画像を検証・固定→候補カードともっと見る生成→固定共有ページ作成→返信。再取得・再計算・画像生成なし |
| 活動時間・計算設定変更 | 設定保存→保存済み予定と調整→計算→候補→保存・公開 |
| 除外日変更 | 設定保存→保存済み多忙度から候補のみ→保存・公開 |
| 探索期間変更 | 範囲内は候補再選出。不足する取得範囲があれば取得から |
| 時間帯編集・解除 | 調整保存→保存済み予定と調整→計算→候補→保存・公開 |
| 共有許可・解除 | 許可と版の変更。予定取得なし。解除は閲覧・待機送信も停止 |
| 共有閲覧 | 固定版のトークン・期限・許可版を確認。再取得なし |

毎日の自動更新は初版では起動しない。stageは操作ごとに必要なものを使い、計算前の設定保存等でpersistを複数回通り得る。[ログ仕様](logs.md)参照。

## 5 保存と公開

保存データは標準User＋7種類。[DB草案](schema.md)の所有者・公開範囲を維持する。

- Google入力形式、計算用形式、保存形式、表示用データを区別し、M09／M08が変換する。
- CalendarSourceは完全取得の必要項目だけ。normalizeの戻り値をそのまま保存しない。
- 日別・時間別・候補・画像は同じ結果版を参照する。画像生成は共有用の限定項目から行い、画像準備の失敗で計算成功を取り消したことにしない。
- 保存前の集計データから直接UI・共有へ流さない。完成版を検証して参照を切り替える。
- 活動時間・調整・除外等で候補や表示が変わったときも、新しい完成版用の画像を準備する。画像と結果が一致しない一式は共有準備完了にしない。
- 最新参照の競合保証はP05。版を読んで比較するだけで原子性があるとはしない。

## 6 失敗と送信

| 失敗 | 扱い |
| --- | --- |
| Google取得・不完全取得 | 前回表示を古さ付きで残す。対象候補を無効化。古い候補をLINEへ代用しない |
| 調整保存後の再計算 | 保存と計算の成否を分ける |
| 計算・DB保存・公開 | 新版を公開しない。原因を段階別に記録 |
| 古い実行 | superseded。最新成功runの候補状態を変更しない |
| LINE明示拒否 | runはfailed、delivery_state=failed。保存済み結果は保持 |
| LINE受理不明 | runはfailed、delivery_state=unknown。無条件再送しない |
| DB読取不能の共有閲覧 | 有効性を確認できないので公開しない |

計算・保存の失敗案内を送れた場合もrunの業務失敗は残す。署名不正・本人未特定は受付ログで追い、偽のowner_idでOperationRunを作らない。

## 7 検証

[権限表](access.md)、[確認リスト](checks.md)、[判断待ち](decisions.md)を使う。終日は設計の6時間換算を維持し、現実装との差と合成判断P04を記録する。時間帯調整・日時・実行基盤の詳細を未承認で実装しない。


## 8 画像・カードの追加境界

WebUIの共有描画→画像保存アダプターと、保存済み画像／候補→カード組立を分離する。画像生成側とLINE側はsnapshot ID等の参照で接続し、LINE依頼からブラウザの起動を要求しない。画像未準備・古い候補・日付経過・同時更新の判定と保存項目はP13。文面を変えても計算結果そのものを書き換えず、文面の版を分ける（P14）。
