# LINEグループでの候補日カード自動生成

更新日：2026-10-18。目標仕様。製品本体の実装・実機確認は未実施。従来のLINE依頼時の予定再取得を変更し、カレンダー更新時の画像保存と＠リスケ時のカード生成を分離する。

## 1 カレンダー更新と画像保存

1. Web側でGoogle予定の取得、承認済み調整、集計、候補選出を行い、完成版を保存する。
2. 更新済みWebUIの共有用月間カレンダー部分を画像化する。月間画像を1枚保存し、すべての候補カードで共用する。
3. 画像は元の結果版に対応付ける。画面全体、予定名・本文、本人専用設定・秘密を含めない。
4. 計算完了と画像保存完了を別に記録する。画像生成・保存の失敗で計算済み結果を消さない。
5. 設定・時間帯調整・除外等で結果が変わったときも、対応する版の画像を準備する。

画像の描画方式・保存先・権限・配信URL・準備状態の具体設計はP13。WebUIの共有用要素を画像化する要件であり、LINE依頼時にブラウザを開いて描画する設計にはしない。初版の自動更新スケジュールは追加しない。

## 2 ＠リスケでの生成・返信

1. LINE受信本文の署名、＠リスケの依頼判定を行う。全角キーワードを指定し、半角互換・完全一致・実メンション要否の厳密な判定はP07で決める。
2. 検証済みuserIdから本人対応と対象グループの共有許可を確認。表示名を本人識別にしない。
3. 有効依頼を耐久受付し、別の実行担当が処理する。受付HTTP成功は返信完了ではない。
4. 保存済み完成版・候補・月間共有画像の所有者・版・利用可否を検証して、使う元版を固定する。
5. 同じ月間画像を使い、候補日の数だけ説明付きカードを自動生成する。候補は従来どおり最大3件。
6. 候補ありなら最後にもっと見るカードを追加し、同じ元版の共有ページへリンクする。
7. 送信直前にも現在のグループ許可・許可版を確認し、返信結果を記録する。

＠リスケではGoogle再取得・再計算・画像生成を行わない。保存済みデータの再利用であり、その時点のGoogle予定と一致する保証ではない。取得日時・画像生成日時を表示し、古さを隠さない。未準備・版不一致・日付経過時の具体案内はP13。

同じ画像・結果を再利用してカード一式を新しく生成しても、既に送ったカードや共有ページを上書きしない。同じイベントの再送は新しい依頼として再生成しない。

## 3 カード一式の項目

| 項目 | 仕様 |
| --- | --- |
| 管理用アイテム名 | アイテムID。生成一式を追跡する内部管理名 |
| 候補カード数 | 候補日数。最大3件、1〜2件はある分だけ |
| 写真 | 更新時に保存した月間の抽象化カレンダー画像。全候補で共用 |
| カードタイトル | 候補日のID。識別子の形式・長さ・日付表示はP07/P14 |
| 説明文 | 「[予定が入っている時間]は予定があり、それ以外は空いている」趣旨。文面は変更可能 |
| アクション1 | この候補を提案する |
| 投稿テキスト | 「[予定が入っている時間]以外の時間帯なら予定を入れます」趣旨。文面は変更可能 |
| 最後のもっと見るカード | 同じ画像・候補の元版を参照する固定共有ページのURL。Webホームや本人の最新版へは飛ばさない |

日付と対象活動時間が分かる文面にする。例：「10月20日は、13〜14時・16〜18時以外の活動時間内なら予定を入れられます」。これは文面例で、確定した予定・全員の空き・予約を意味しない。終日換算の6時間から架空の予定区間を作らない。

ボタンは押した人の発言として提案テキストを投稿する。投票・参加表明・予約確定データは保存しない。編集方法・公開範囲・文面版はP14。

Bot側の自動組立を基本案とし、Flex Message等で実現する具体方式はP07。LINE管理画面のアイテムと応答ルールを自動登録することは必須ではない。内部のitem IDを、実在するManagerアイテムのIDと混同しない。

## 4 正常0件と未準備

有効な保存済み完成版で候補0件なら「候補日が見つかりませんでした」と案内し、候補カード・もっと見るを作らない。画像の未保存や版不一致を正常0件へ変換しない。

画像準備失敗、候補の日付経過、設定変更後、更新中の利用可否はP13で相談する。別版の画像と候補を混ぜたり、古い候補で暗黙に代用したりしない。

## 5 公開内容と許可

画像、日別／時間別多忙度、候補、抽象化された多忙時間帯、説明・提案文を公開対象として許可画面で説明する。予定名・本文・認証情報・LINE識別子は公開しない。

画像保存だけでグループ公開としない。本人連携、Google利用者別認可、本人×グループの共有許可は別管理。LINE依頼はGoogle APIを呼ばず、保存済み結果を使えるかを検証する。Google解除時の既存結果の扱いはP09。

リンクは知っている人が転送先でも閲覧できる。解除は対象の旧共有版・待機送信へ反映し、再許可しても旧版は復活しない。画像配信にも権限と期限の設計が必要（P13）。LINEへ取得・配信済みの画像・カード・テキストを回収できるとはしない。

## 6 期限・失効

共有ページは最終候補日後、発行から最大1カ月で失効する。月末・境界はP08。再生成で期限の基準を無制限に延長しない。元の候補が利用可能かも確認する。

期限切れ・解除後は情報を返さず案内する。画像・スナップショット・ログの保持と削除は別処理P09/P13。

## 7 ログと検証

更新runは計算・保存→render_share_image→画像保存の成否を追い、LINE runは既存版読込→prepare_shareでカード組立→固定共有保存→deliverを追う。LINE側で元版のresult_snapshot_id、画像参照、文面版、カードIDを対応させる。具体保存先は現JSONCに未定義でP12〜P14。

受理はsent、明示拒否はfailed、受理不明はunknown。無条件再送なし。API秘密・返信トークン・共有生トークン・画像配信用の秘密URL・本文全文をログへ出さない。

[確認リスト](checks.md)のV22〜V26、V32〜V36を使い、＠リスケ時の再取得・再描画がないこと、画像・説明・候補・共有ページの版一致、0〜3件、提案投稿、許可解除、失敗・再送を確認する。独立Botの疎通成功を製品の合格にしない。

## 画像テストとして承認した範囲（2026-10-18）

年月・予定時刻を画像から推測せず、候補・時間帯はテスト用の固定値と明記。

画像はBase44関数の固定公開GETで配信し、カードと同じimage-demo-v1で参照する。
