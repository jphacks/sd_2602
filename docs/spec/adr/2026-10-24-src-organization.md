# ADR: srcの機能別整理と段階的な移行

- 決定日：2026-10-24
- 状態：整理方針を記録。配置案は移行時の参照確認で調整する。
- 実装状態：未着手。この文書の作成はコード整理・テスト完了を意味しない。

## 背景

現在はroutes、components、libに責務が分かれている一方、同じ機能の画面と処理が複数の場所にある。機能を追いやすくし、認証・保存・外部APIに依存しない計算を区別するため、段階的な整理を行う。

個人デモとGoogle取得では共通計算とPersonalPageを既に使用する。全画面が独立した重複実装という前提で作り直さない。README、設計、コードの差は移行前に確認し、コードの存在と実接続の検証済みを区別する。

## 決定

1. 未使用候補を参照調査してから削除する。検索で参照がないことだけでは削除を確定しない。
2. 機能固有の画面と処理をfeaturesへ、サービス非依存の予定計算をdomain/scheduleへ、実際に共有される部品をsharedへ分類する。
3. routesの配置・URL・認証ゲート、api/base44Client.jsの指定位置、router.jsxとstart.jsの役割は最初の整理では維持する。
4. まず個人デモの小さな範囲で整理する。認証、DB、Google、LINEへ影響する移動は後続の独立した変更とする。
5. ファイル移動、処理の共通化、機能追加、TypeScript移行、クラウド移植は別の変更にする。今回はJavaScript/JSXを維持する。
6. 共通形式は既存の入出力契約を優先する。必要ならJSDocで説明するが、新しい型や形式を無断で再定義しない。外部入力の実行時検証は残す。
7. デモデータと実データの入口・表示ラベルを維持する。保存なしの画面に新たな保存を加えない。

## 配置案（確定した移動一覧ではない）

```text
src/
  routes/                       URLの入口を維持
  features/
    personal/                   個人画面・取得の入口・デモ
    pair/                       比較画面・比較処理・デモ
    google-calendar/            外部取得と共通形式への変換
    auth/                       認証画面・状態管理・本人確認
    settings/                   設定・調整ルール
  domain/schedule/              正規化・多忙度・候補選出
  shared/                       共通UI・Hook・共通の日時処理
  api/base44Client.js            指定位置を維持
  mock/                         再現可能な固定データ
  index.css
  router.jsx
  start.js
```

各機能は必要な場合だけcomponents、server、demoなどに分割する。運用履歴やカレンダーソース管理をsettingsに押し込まず、責務を調査して分類を決める。domainはReact、Base44 SDK、外部通信に依存させず、時計は必要に応じて引数から渡す。画面からサーバー実装を直接読み込まず、フレームワークのサーバー関数経由で呼ぶ。serverというフォルダ名だけでは機密性は保証されない。

## 削除・統合の調査候補

- 未使用のUI部品、Hook、補助関数。
- AI関連コードと依存パッケージ。ただし参照・設定・今後の採用判断を確認する。
- api/time.js、server-fns.jsなどの初期確認用途の処理。公開URL利用や動的参照も確認する。
- 同じ意味・タイムゾーン・境界条件を持つ日付処理、読み込み状態表示、サーバー応答設定。

認証ページ群、Base44の仮想モジュール、生成ファイル、プラグインの自動探索対象は通常のimport検索だけで判断しない。純粋な中継ファイルもサーバーとブラウザの境界を作るために必要な場合がある。

## 注意点と対策

| リスク | 対策 |
| --- | --- |
| importや相対パスが切れる | 参照元と移動先の対応表を作り、テストとビルドで確認 |
| URL・認証制御が変わる | routesとゲートを維持し、匿名・ログイン済みの両方で確認 |
| サーバーコードがブラウザへ混入 | import経路と生成物を確認し、秘密の値を出力・記録しない |
| 計算結果や日時が変わる | 固定入力と固定時刻で移行前後を比較 |
| 共通化しすぎる | 同じルールだけ共有し、個人と比較の異なる条件は分離 |
| デモと実接続の混同 | 入口・ラベル・保存有無を維持し、未検証を明示 |
| 大量移動でレビュー不能 | 小さな単位で確認・コミットし、機能変更を混ぜない |
| ボリュームや秘密情報を失う | 整理のためのボリューム削除・環境初期化を行わない |

## 代替案と判断

- 現状維持：変更リスクは最小だが、機能を追う移動が残る。
- frontend/backendへ一括分割：実行場所は見やすいが、機能の関連が再び分散し、フレームワーク境界もあるため今回は採用しない。
- 機能別整理を段階実施：共通計算を残しつつ理解しやすくできるため採用する。

## 期待する結果と限界

同じ機能の変更箇所を見つけやすくし、外部基盤に依存するコードを識別しやすくする。配置変更だけで速度改善・型安全性・セキュリティ向上・コード量削減を達成したとは扱わない。移行中は新旧配置が共存するため、完了した範囲を記録する。

## 検証・中止・復旧

[整理チェックリスト](../../dev/src-reorganization-checklist.md)で変更前後の結果と証拠を記録する。開始時点で失敗する検査は既存問題として記録し、新たな失敗と区別する。失敗を解消できない単位は先へ進めず、当該差分だけ修正または取り消す。他の未コミット変更を破棄しない。公開・実LINE送信・DB変更は、この整理の確認手段として自動実行しない。
