## データの準備
- ユーザーはテスト用データを事前に用意し、まずローカルで簡単な仮データを使う意向。
- 提案：JSON等の固定データをGit管理し、DBへ再投入できる原本にする。実在の予定・秘密情報は含めない。
- 正常、重複、日跨ぎ、終日、活動時間外、正常な予定0件、4人比較を用意する。
- Google取得失敗、AI失敗、不正応答、保存失敗、古い応答はモック等で再現する。
- LINE未連携、未許可、候補0〜3件、解除・再許可・期限、再送・送信失敗を追加する。
- ローカルDBは採用するBase44構成を確認して決める。別のDB製品を自動的に追加しない。
- 共有確認はBase44のTest Data、公開版は発表専用データを使う案。利用可能性・接続先を実機確認する。

## 当日までの準備と合格条件
1. 2人がGitHubのリポジトリへアクセスし、ブランチとPRを作れる。
2. 同じ手順でローカル起動・仮データ投入・テストを実行できる。
3. 小さな変更でレビューからBase44反映・公開まで一巡確認する。
4. 実APIの認可準備、接続先、Secrets、外部呼出しの有無を確認する。
5. 機能ごとに担当・受入条件・依存関係を決める。

## 機能単位の開発フロー案
1. 最新mainから機能ブランチを作る。実装プランと受入条件を確認する。
2. 仮データ・モックで実装し、必要な単体テストと画面操作を確認する。
3. PRに目的、変更内容、確認結果、未確認事項、フラグ・使用データを記載する。
4. 相手がブランチをローカルに取得し、初期データから再現・レビューする。
5. 修正・再確認・承認後にmainへ統合し、統合後の動作も確認する。
6. Base44のテストデータでクラウド上の通し確認を行う。
- developは当初設けず、短い機能ブランチで進める案。
- 同じブランチ・ファイルをローカルとBase44で同時編集しない。
- DB構造・権限・Secretsなど共有設定の変更は事前に担当間で調整する。

## Feature Flagの方針案
- 新機能は初期OFFにし、開発者のみONで確認する。サーバー側でも対象者を判定する。
- フラグは認証・権限制御やデータ分離の代用ではない。
- 機能ON/OFFと、モック/実APIの接続切替は別設定にする。
- OFF、ON、ONかつ外部処理失敗を確認し、公開予定の組合せでもテストする。
- 目的・初期値・削除時期を記録する。OFFでもDB変更や外部送信は元に戻らない。

## 2日間の配分案
### 1日目
- 開始時：最新コード、起動、データ投入を2人で確認。
- 午前：仮予定→正規化→多忙度→画面表示を一度通し、最初のレビュー・統合。
- 午後：候補日・設定保存等を機能ごとに追加し、相互レビュー・統合。
- 終了前：共有環境で通し確認し、翌日の修正対象と削る機能を整理。
- 最初の分担案：Aは画面、Bは計算処理。受渡し型を先に合わせる。確定担当ではない。
### 2日目
- 朝：統合済みの主要シナリオを再確認。
- 午前：必要な実API接続と失敗時動作を確認。
- 昼：機能追加を止め、発表に含める機能を確定。
- 午後：不具合、権限、保存、共有を確認し、公開とリハーサル。
- 最後：発表版のコミットを記録し、変更を止める。
- デモ初期化手順と外部接続不能時の代替手順を用意。モック使用は明示する。
